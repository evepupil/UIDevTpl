## 1. 规范目的

本规范定义一套 UIDevTpl 模板需要包含什么、代码如何分层、不同平台与框架如何共用视觉语言、如何迁移到用户项目，以及达到什么标准才能发布。

规范追求四个结果：

1. AI 能快速看懂模板源码并迁移需要的部分。
2. 用户换业务内容后，页面仍然保持原模板的审美。
3. 同一视觉家族可以面向不同平台和框架独立实现，每个实现符合目标生态习惯。
4. 网站预览、下载模板包和参考图使用同一固定版本源码。

## 2. 已确认的模板决策

| 编号 | 决策 | 要求 |
| --- | --- | --- |
| T-001 | 视觉家族与代码实现分开 | 家族保存审美基线，模板实现保存框架源码 |
| T-002 | React/Vue 独立实现 | 不发布自动翻译生成且未经完整验收的跨框架代码 |
| T-003 | 模板 ID 包含平台和技术栈 | 使用 `<platform>/<framework>/<component-library>/<template>` |
| T-004 | 组件库不绑定应用场景 | 同一组件库可以有多种风格，同一风格可以验证多个题材 |
| T-005 | 真实源码是交付主体 | 截图和文字规则用于验证与说明，不能代替源码 |
| T-006 | 原子化分层 | Atoms、Composites、Layouts、Page Skeletons、Showcase 职责分开 |
| T-007 | 语义 token 驱动 | 组件消费语义角色，禁止散落未登记的视觉值 |
| T-008 | 完整状态 | 真实组件展示所有适用状态和交互 |
| T-009 | 固定版本 | 已发布家族版本和实现版本保持不可变 |
| T-010 | 迁移后可追溯 | 原始模板保存在 `.uidevtpl`，目标文件记录迁移映射 |
| T-011 | 平台与宿主分开 | `platform` 进入模板 ID；浏览器、Electron、Tauri、Expo 等 `runtime` 写入 Manifest 兼容信息 |
| T-012 | 组件实验室独立 | 组件实验室不计入每个实现至少两个完整 Showcase 的数量 |
| T-013 | V1 授权 | UIDevTpl 自有模板代码使用 MIT，品牌资产和第三方资产单独授权 |
| T-014 | 固定版本预览 | 生产 Showcase 使用 Vite MPA 构建，每个模板版本和 Showcase 拥有独立静态入口 |
| T-015 | 平台构建隔离 | 主站不导入模板运行时代码；模板预览、模板包和兼容性验证分别构建并由同一 Manifest 绑定 |
| T-016 | V1 shadcn/ui 主线 | V1 公开 React 模板统一使用 shadcn/ui；其他组件体系保留模型与后续独立实现空间 |
| T-017 | 源码所有权隔离 | 官网和每个模板实现分别拥有自己的 shadcn/ui 组件源码，禁止通过共享运行时 UI 包形成发布耦合 |
| T-018 | Registry 派生产物 | 固定 ZIP 和 Manifest 是发布权威，shadcn Registry Item 必须从同一版本源码生成并进入校验记录 |

## 3. 核心模型

### 3.1 视觉家族

视觉家族是一套可跨平台复用的审美基线，负责定义：

- 颜色角色与主题。
- 字体、字阶、行高和文本宽度。
- 间距、密度、圆角、边框和阴影。
- 动效时长、缓动和降级方式。
- 图片、图标和内容规则。
- 公共构图原则，以及各平台的网格、断点、触控或窗口布局结果。
- 组件能力、状态和无障碍验收要求。
- Showcase 使用的公共 fixture 和视觉评审标准。

示例：`quiet-grid@1.0.0`。

### 3.2 模板实现

模板实现是视觉家族在指定平台、框架和组件库上的真实代码，负责定义：

- 组件源码和公开 API。
- 组件库主题映射与封装。
- 框架状态逻辑。
- Provider、插件和应用入口接入。
- 布局组件与页面骨架代码。
- Showcase 和组件实验室。
- 框架专属迁移说明。
- 兼容版本与验证结果。

示例：

```text
web/react/shadcn/quiet-grid@1.0.0
web/vue/reka/quiet-grid@1.0.0
```

两个实现可以引用同一个 `quiet-grid@1.0.0` 家族版本，也可以拥有不同的实现版本。

### 3.3 共享与独立边界

| 内容 | 权威来源 | 跨框架要求 |
| --- | --- | --- |
| 语义 tokens 和取值 | 视觉家族 | 共享相同角色和家族版本 |
| 字体、图片、图标、动效规则 | 视觉家族 | 共享视觉与授权标准 |
| 公共构图原则 | 视觉家族 | 保持同一审美与内容层级 |
| 断点、触控、窗口和安全区结果 | 视觉家族的平台规则 | 同平台使用相同验收条件 |
| fixture 和参考内容长度 | 视觉家族 | 使用相同数据便于比较 |
| 组件能力和状态要求 | 视觉家族 | 逐项建立实现映射 |
| 组件源码 | 模板实现 | React/Vue 独立维护 |
| 组件 API、props、slots、events | 模板实现 | 遵循各自框架习惯 |
| 路由、Provider、插件和状态逻辑 | 模板实现 | 独立实现与验证 |
| 组件库主题适配 | 模板实现 | 绑定明确组件库版本 |
| 迁移说明 | 模板实现 | 针对目标项目分别编写 |

允许直接共享的代码限于与框架无关的内容，例如 JSON、CSS 自定义属性、Schema、纯数据和纯转换函数。React 实现不能运行时导入 Vue 源码，Vue 实现也不能运行时导入 React 源码。

## 4. 标识与版本

### 4.1 命名规则

模板 ID 格式：

```text
<platform>/<framework>/<component-library>/<template>
```

要求：

- 全部使用小写 ASCII。
- 单词之间使用连字符。
- ID 发布后保持稳定。
- 平台、框架或组件库变化时创建新的模板 ID。
- 运行宿主变化时优先在 Manifest 中增加兼容项；宿主导致源码、页面契约或迁移方式明显分叉时创建新的模板实现。
- 同一视觉家族在不同框架下使用相同 `<template>` 名称，便于关联。
- 名称不能使用参考产品的品牌或内部标识。

示例：

```text
web/react/shadcn/quiet-grid
web/vue/reka/quiet-grid
web/react/shadcn/high-contrast-editorial
```

### 4.2 版本规则

视觉家族和模板实现分别使用语义化版本。

视觉家族：

- Major：核心视觉语言、必填 token、布局契约或强制规则发生不兼容变化。
- Minor：新增主题、token、页面骨架契约或可选规则。
- Patch：修正文档、参考资产或不改变视觉结果的遗漏。

模板实现：

- Major：公开组件 API、迁移方式或框架接入发生不兼容变化。
- Minor：新增组件、页面骨架、Showcase 或兼容范围。
- Patch：修复类型、无障碍、实现错误或不改变主要外观的问题。

实现只修复 React 代码时，可以发布新的 React 实现版本并继续引用原家族版本。家族版本升级后，各实现独立决定何时跟进，网站必须如实显示当前引用关系。

### 4.3 制作状态与公开可用性

模板 Manifest 的 `status` 表示制作状态：

- `draft`：制作中，只在本地或内部环境可见。
- `review`：等待技术和视觉评审。
- `published`：通过全部门禁，公开模板包内固定为该值。

网站发布记录的 `availability` 表示公开可用性：

- `active`：进入最新稳定解析、公开列表、搜索和下载。
- `deprecated`：仍可查看和下载，不建议新项目使用。
- `withdrawn`：因安全、许可证或错误产物停止分发，只保留最小版本记录、原因和替代版本。

一个视觉家族的 React 实现可以先发布，Vue 实现保持 `draft`，互不阻塞。模板包、Manifest 和 SHA-256 发布后保持不可变；弃用与下架只修改带审计记录的 `availability`。`withdrawn` 不能恢复为 `active`，修复后发布新版本。

- 下载包 SHA-256 在发布后不可改变。

### 7.1 网站发布记录

公开网站使用独立发布记录承载可变的可用性，最低结构如下：

```json
{
  "templateId": "web/react/shadcn/quiet-grid",
  "version": "1.0.0",
  "availability": "active",
  "artifact": {
    "url": "https://<uidevtpl-domain>/artifacts/web/react/shadcn/quiet-grid/1.0.0/template.zip",
    "sizeBytes": 1234567,
    "sha256": "<sha256>"
  },
  "publishedAt": "2026-08-10T00:00:00Z",
  "availabilityChangedAt": "2026-08-10T00:00:00Z",
  "availabilityReason": null,
  "replacement": null
}
```

- 发布记录首次生成时，身份、版本和产物信息必须来自已经通过门禁的 Manifest 与模板包。
- 发布后只有 `availability`、`availabilityChangedAt`、`availabilityReason` 和 `replacement` 可以通过受审计操作修改。
- `deprecated` 和 `withdrawn` 必须填写原因；存在替代版本时使用完整模板 ID 和固定版本。
- 页面、搜索、sitemap、缓存和下载入口统一读取发布记录，不能各自维护状态副本。

### 7.2 目录条目与社区扩展

模板包 Manifest 和固定发布记录只描述可复现产物。首页、Category、分享者和热度使用独立目录条目：

```json
{
  "id": "entry_quiet_grid_workspace",
  "templateId": "web/react/shadcn/quiet-grid",
  "templateVersion": "1.0.0",
  "showcaseId": "ai-project-workspace",
  "categories": ["applications", "dashboards"],
  "publisher": {
    "id": "publisher_uidevtpl",
    "displayName": "UIDevTpl Studio",
    "avatarUrl": "https://<uidevtpl-domain>/avatars/uidevtpl.png",
    "type": "official",
    "profilePath": "/creators/uidevtpl"
  },
  "source": "official",
  "visibility": "public",
  "moderationStatus": "approved",
  "metrics": {
    "views": 12800,
    "likes": 936
  },
  "sharedAt": "2026-08-10T00:00:00Z"
}
```

要求：

- `templateId` 与 `templateVersion` 必须解析到 `active` 的固定发布记录，目录条目不能改写产物身份。
- `showcaseId` 必须存在于对应模板 Manifest，并决定卡片缩略图和详情默认预览。
- Category 使用稳定 ID 和独立中英文名称；一个条目可以属于多个 Category。
- `publisher` 表示公开分享身份；模板代码作者与版权归属继续从许可证记录读取。
- 公开列表只展示 `visibility: public` 且 `moderationStatus: approved` 的条目。
- 浏览量和点赞数是可变聚合数据，不写入 Manifest、模板包或固定版本校验值。
- 当前访问者的点赞状态单独存储并按账号或匿名会话去重，缓存目录记录时不能混入个人状态。
- 用户投稿开放后仍生成同一结构的目录条目，先经过审核再进入公开列表。

## 8. 代码分层

### 8.1 依赖方向

```text
Foundations
  -> Atoms
  -> Composites
  -> Layouts
  -> Page Skeletons
  -> Showcase
```

规则：

- 依赖只能沿箭头向右。
- 下层不能导入上层。
- 层与层之间不能循环依赖。
- Showcase 可以依赖所有层，其他层不能依赖 Showcase。
- 页面骨架不能依赖具体 Showcase 数据文件。
- AI 迁移某一层时，需要同时迁移它依赖的下层文件。

### 8.2 原子化尺度

原子化的目标是让组件职责清楚、方便组合和迁移。拆分需要带来真实价值。

不要求：

- 每个 HTML 标签单独做一个组件。
- 只有一行样式的包装层全部抽象。
- 为一次性静态内容创建大量无意义文件。

需要拆分的情况：

- 具有独立视觉规则和状态。
- 在多个组合或页面骨架中复用。
- 包含需要单独验证的交互和无障碍行为。
- 具有稳定输入输出接口。
- 继续放在父组件中会让职责混乱。

组件出现大量互相冲突的布尔属性时，应拆分清晰变体或独立组件，避免形成难以预测的万能组件。

## 9. Foundations 规范

### 9.1 Token 层级

允许两层 token：

1. Primitive：原始色阶、基础尺寸和数值，只供主题映射使用。
2. Semantic：描述用途，例如 `surface-default`、`text-muted`、`action-primary`。

模板组件只能消费 Semantic tokens。Primitive tokens 不能直接散落在组件和页面文件中。

### 9.2 最低 token 分类

- Color：页面背景、普通表面、浮层、正文、弱化文字、边框、主操作、次操作、成功、警告、错误和信息。
- Typography：字体家族、字号、字重、行高、段落宽度和文字用途。
- Spacing：基础单位、组件内距、组件间距、区块间距和页面边距。
- Shape：圆角、边框宽度、分割线和控件形状。
- Elevation：普通表面、菜单、浮层、弹窗和强调元素。
- Motion：即时反馈、普通过渡、页面进入和 reduced-motion 行为。
- Layout：内容最大宽度、侧栏、网格、断点和固定工具栏尺寸。
- Media：图片比例、裁剪方式、遮罩、图标尺寸和插图规则。

### 9.3 Token 要求

- 角色命名表达用途，避免 `blue-500-button` 这类绑定具体颜色的语义名。
- 每个实现声明支持的主题都提供完整值；未完成的主题文件和主题声明不能进入公开包。
- 组件库主题配置可以追溯到语义 token。
- 组件文件禁止直接写未登记十六进制颜色、任意圆角和任意阴影。
- 例外值必须登记、说明用途并通过视觉评审。
- CSS 自定义属性具有稳定前缀，避免污染用户项目现有变量。
- token 变更需要生成可读差异。

### 9.4 字体

- 记录字体来源、版本、许可证和允许用途。
- 提供本地或远程加载方式及 fallback。
- 字体不可用时，文本不能严重溢出或遮挡。
- 字阶数量保持克制，每一级写明用途。
- 组件内紧凑标题不能使用页面 Hero 级字号。
- 字间距默认为 0；特殊品牌字样需要单独说明。

### 9.5 响应式

- 家族定义公共验收视口：360 x 800、768 x 1024、1440 x 900。
- 允许实现使用框架或样式系统的断点写法，最终布局结果需要一致。
- 固定格式元素使用明确尺寸、比例或网格约束。
- 动态文字不能改变按钮、工具栏、计数器和预览控件的整体布局。
- 长单词、模板 ID 和业务数据需要有换行、截断或滚动策略。

## 10. 原子组件规范

原子组件负责一种清晰的界面能力，例如 Button、Field、Badge、Avatar、Divider 或 StatusIndicator。

必须满足：

- 通过 props、slots 和 events 接收内容与行为。
- 不绑定业务接口、路由、持久化存储和全局业务状态。
- 不写死品牌名、产品名、价格、用户身份和业务枚举。
- 不包含页面宽度、页面边距和路由级布局逻辑。
- 只使用登记的语义 tokens 和组件 recipes。
- 公开变体有限、可说明、可完整预览。
- 保留底层组件库成熟的键盘、焦点、表单和弹层行为。
- 可访问名称、帮助文本和错误信息可由调用方提供。
- 类型清晰，禁止大面积使用 `any`。

每个公开原子组件必须提供：

- 组件目的。
- 公开 API。
- 默认值。
- 支持变体。
- 状态矩阵。
- 最小使用示例。
- 禁止用法。
- 依赖的 token 和底层组件库能力。

通用组件使用职责命名，例如 `Button`、`Field`、`StatusBadge`。业务命名组件只能留在 Showcase。

## 11. 组合组件规范

组合组件将多个原子组件组合成稳定、可跨业务复用的界面片段，例如 SearchBar、FilterToolbar、EmptyState、DataToolbar 或 PricingSummary。

必须满足：

- 数据、权限结果、加载状态和业务操作由外部传入。
- 可以维护展开、选中、输入草稿等短期界面状态。
- 不直接发起业务请求，不写入数据库，不决定业务路由。
- 不重复实现原子组件已有样式和行为。
- 提供清晰内容插槽，让 AI 替换内容时保留构图。
- 明确手机端换行、折叠或替代布局。
- 复杂键盘交互有说明并经过浏览器验证。

行业专属结构先放在 Showcase。确认能够跨业务复用并完成抽象后，才进入 `composites/`。

### 11.1 V1 最低组件能力

V1 的每个公开实现至少提供以下能力；实际组件名称可以遵循目标生态习惯：

| 类别 | 最低组件或能力 |
| --- | --- |
| 操作与展示 | Button、IconButton、Link、Badge、Avatar、Divider |
| 表单输入 | Input、Textarea、Select、Checkbox、Radio、Switch |
| 导航与浮层 | Tabs、Accordion、Pagination、Tooltip、Dropdown、Popover、Modal、Drawer、Toast |
| 数据与状态 | Table 或 DataList、SearchBar、FilterToolbar、EmptyState、ErrorState、Skeleton |
| 页面布局 | SiteShell、AppShell、Sidebar、PageHeader、ContentLayout、ResponsiveNavigation |

某项能力确实不适用时，需要在 Manifest 和状态矩阵中写明原因，并在发布评审中单独批准。不能用遗漏代替取舍记录。

## 12. 布局组件规范

布局组件管理页面区域关系、网格、滚动和响应式行为。

每个视觉家族需要定义：

- 页面容器和最大宽度。
- 顶部导航、侧栏、标题区和内容区尺寸范围。
- 页面边距和区块间纵向节奏。
- 卡片、普通内容区和分割线的使用边界。
- 列表、详情、表单和数据展示的基础构图。
- 手机端侧栏、表格、筛选器和操作区如何变化。
- 固定、吸顶和悬浮元素的允许范围。
- 遮挡规避和安全区域处理。

布局组件不读取业务数据，不判断业务权限，不发起网络请求。区域内容通过 children 或 slots 注入。

## 13. 页面骨架规范

每个公开模板至少提供三类页面骨架：

- 营销页：品牌、产品、服务或活动展示。
- 应用界面：工作台、管理、工具或操作型页面。
- 内容页：文章、文档、知识库、媒体或详情阅读。

页面骨架必须：

- 固化主要构图和响应式关系。
- 接收结构化数据与动作接口。
- 标注必选区域和可选区域。
- 标注推荐标题、正文、标签和列表长度。
- 提供页面级 Loading、Empty、Error 和权限不足的放置方式。
- 不连接真实认证、支付、数据库和业务 API。
- 不依赖具体 Showcase fixture。

AI 可以复制页面骨架并替换业务区域。基础布局和视觉层级应尽量保留，确需改变时需要解释业务原因。

## 14. Showcase 与组件实验室

### 14.1 Showcase

Showcase 用于证明模板能够形成完整产品页面。每个模板实现至少提供两个不同题材，组件实验室单独计算。

要求：

- 两个题材具有明显不同的信息结构和内容类型。
- 使用同一套 tokens、组件和布局规则。
- 交互可真实操作。
- 演示状态使用本地 fixture，可一键重置。
- 默认不发起外部网络请求；经过审核的固定演示资源写入网络白名单。
- 不执行真实登录、支付、订单、邮件和外部数据写入。
- 不伪造尚未实现的业务能力。
- 桌面和手机都形成完整、可检查的页面。
- 主要图片展示真实业务主体，避免只用模糊氛围图。

### 14.2 组件实验室

组件实验室展示模板的真实组件入口，不能另写一套静态外观。

要求：

- 按组件类别组织，便于查找。
- 显示支持的尺寸、颜色和视觉变体。
- 展示全部适用状态。
- 支持键盘操作。
- 可以查看深色和浅色主题，前提是实现声明支持。
- 组件示例区域尺寸稳定，状态切换不能挤压其他内容。

## 15. 状态矩阵与交互

每个实现提供机器可读的 `state-matrix.json`。组件按能力覆盖：

- Default。
- Hover。
- Focus visible。
- Active 或 Pressed。
- Selected 或 Checked。
- Disabled。
- Loading。
- Invalid 或 Error。
- Empty。
- Success。
- Open 或 Expanded。

不适用的状态使用 `notApplicable` 并写明原因。遗漏、`null` 和空字符串不能代替说明。

弹窗、菜单、选择器、Tabs、Accordion 和其他复合交互还需要验证：

- 键盘进入、操作、切换和退出。
- 初始焦点和关闭后的焦点归还。
- Escape、点击外部和重复触发。
- 浮层层级、滚动锁定和窄屏定位。
- Loading、失败和快速重复操作。
- 受控与非受控模式，适用时分别说明。
- `prefers-reduced-motion` 下的替代行为。

## 16. 图片、图标与内容

### 16.1 图片

每个视觉家族必须说明：

- 首选图片类型，例如产品实拍、人物、场景或无图片。
- 图片亮度、背景、裁剪和宽高比。
- 滤镜、蒙层和圆角的允许范围。
- 桌面和手机的主体保留区域。
- 缺图、加载中和加载失败状态。

### 16.2 图标

- 明确图标库和许可证。
- 统一默认线宽、尺寸和视觉重量。
- 图标按钮具有稳定可点击区域、可访问名称和 Tooltip。
- 已启用图标库有现成图标时，优先复用。
- 禁止用随意绘制的 SVG 造成风格漂移。

### 16.3 内容

- fixture 不包含真实个人信息、密钥和受限业务数据。
- 文案长度覆盖短、正常和偏长情况。
- 标签、按钮和标题有溢出处理。
- Showcase 文案服务于真实界面，不在页面内解释模板功能或使用方法。
- 应用界面优先保证扫描和反复操作效率。

### 16.4 许可证

所有字体、图片、图标和插图必须记录：

- 来源。
- 作者或版权方。
- 许可证。
- 商用与再分发范围。
- 是否需要署名。
- 模板包中能否包含原文件。

授权不清的资产不能进入 `published`。

UIDevTpl 自有模板代码统一使用 MIT License。UIDevTpl 名称、Logo 和品牌资产不随模板代码授权。`ASSETS-LICENSE.md` 逐项记录资产授权；不能随模板包再分发的资产只提供合法获取方式和降级说明。

## 17. React 与 Vue 兼容规范

### 17.1 基本策略

同一视觉家族分别实现 React 和 Vue。跨框架共享审美与验收标准，源码、组件 API 和生态接入各自维护。

生产发布流程不接受以下做法：

- 把 React 组件改扩展名后作为 Vue 实现。
- 只根据截图生成另一框架代码并跳过人工评审。
- 用一个框架的预览截图代替另一个框架的真实预览。
- 声明支持某框架，却缺少对应源码和迁移说明。

自动生成可以用于内部起稿。进入 `published` 前必须按独立实现完成全部门禁。

### 17.2 同源验收

同一视觉家族发布第二个框架实现前，必须提供 `PARITY.md`，至少记录：

- 两个实现引用的家族版本。
- 核心组件能力映射。
- 状态矩阵映射。
- 页面骨架映射。
- 组件库能力造成的差异及原因。
- 尚未覆盖的能力和公开页面展示方式。
- 同一 fixture、视口和主题下的评审结论。

最低要求：

- 必填语义 token 角色覆盖率 100%。
- 核心组件能力全部映射，缺失项明确标记。
- 使用相同 fixture 和内容长度测试。
- 使用相同桌面、平板和手机视口截图。
- 字体层级、色彩角色、密度、形状、表面层级和主要构图达到同一评分标准。
- 键盘操作、无障碍和响应式满足相同要求。

DOM 结构、props、slots、events 和底层组件组合可以不同。验收关注用户看到和操作到的结果。

### 17.3 独立发布

- React 与 Vue 实现拥有独立版本和发布状态。
- 某个实现升级组件库时，不强制其他实现同时升级。
- 家族规则变化时，每个实现分别验证后发布新版本。
- 网站只显示已经通过门禁的实现。
- 尚未发布的框架可以显示“计划中”，不能提供复制迁移指令。

## 18. shadcn/ui 实现要求

React / shadcn/ui 模板需要记录：

- 生成源码时使用的 shadcn CLI 精确版本与 Registry Schema。
- `components.json` 中的 style、RSC、TypeScript、Tailwind、图标库和路径别名配置。
- 选用的单一底层组件基础及其运行时依赖版本，例如 Base UI 或 Radix。
- 每个组件、Block、页面骨架和 Registry Item 的文件清单与依赖关系。
- 从上游生成后由 UIDevTpl 修改的源码、原因、许可证和追踪方式。
- React、Node.js、TypeScript、Tailwind CSS、构建工具和运行宿主兼容范围。
- Provider、RSC、客户端边界、Portal 和全局样式接入方式。
- 允许的 variants、尺寸、形状、状态和组合方式。
- 需要避免的默认外观、布局和组件组合。

V1 首个实现还需要：

- 以 Node.js `24.x`、React `19.x`、TypeScript `7.x`、Vite `8.x` 和 Tailwind CSS `4.x` 为平台基线；shadcn CLI、Registry Schema、style 与底层组件依赖在首次生成实现时固定精确版本并写入 Manifest、`components.json` 和锁文件。
- 单个实现只使用一种底层组件基础；候选 UI 套件完成许可证、源码再分发、React 19、Tailwind CSS 4、RSC 和无障碍评估后再锁定具体选择。
- 同时通过 Vite React SPA 和 Next.js App Router 的干净项目构建与迁移验证。
- 使用 Vite MPA 生成组件实验室和两个 Showcase 的生产预览入口。
- 在 Next.js 中验证服务端渲染页面、交互组件客户端边界、Portal 和主题初始化。
- 使用 npm 和 pnpm 分别完成至少一次 ZIP 迁移、Registry Item 安装、构建和结果对比。
- 只把经过门禁的组合标记为“已验证”，其他组合标记为“理论兼容”或“不支持”。

官网和每个模板实现分别维护 shadcn/ui 源码。模板运行时禁止导入官网 UI 包，也不能让多个已发布模板依赖一个会继续变化的共享 UI workspace；需要复用的内容通过固定 Registry Item、Schema、纯数据和生成规则传递。

固定 ZIP 与 Manifest 是版本权威。Registry Item 从同一固定源码生成，用于选择性安装；迁移到已有项目时必须先检查目标文件和差异，不能把 `shadcn add` 当作静默覆盖授权。

视觉适配集中在语义 tokens、组件源码、variants 和明确组合层。底层组件已经成熟的键盘、焦点和无障碍行为应保留。Showcase 至少使用两个不同题材验证组件和视觉语言的通用性。

## 19. 必须项与禁止项

每个视觉家族提供结构化规则。例如：

```json
{
  "required": [
    "所有交互元素具有 focus-visible 状态",
    "组件只消费登记的语义颜色角色",
    "独立预览响应浏览器真实视口"
  ],
  "forbidden": [
    "卡片嵌套卡片",
    "组件内直接写未登记的十六进制颜色",
    "用静态截图冒充交互预览"
  ]
}
```

要求：

- 每条规则有稳定 ID，便于检查结果定位。
- 必须项与禁止项不能互相冲突。
- 实现可以增加框架专属规则，不能降低家族强制要求。
- 无法自动检查的规则明确标记为人工视觉检查。
- 规则变更遵循家族版本策略。

## 20. 迁移规范

### 20.1 `MIGRATION.md`

每个模板实现必须说明：

- 支持的平台和运行宿主。
- 支持的框架、组件库、语言模式、样式系统和构建工具版本。
- 模板源码入口和各层依赖关系。
- 必需、可选和冲突依赖。
- tokens、字体、全局样式、Provider、插件和路径别名接入方式。
- 路由、SSR、客户端边界和组件库初始化注意事项。
- 推荐迁移顺序。
- 可以跳过的内容。
- 文件冲突处理方式。
- 回退方式。
- 从旧实现版本升级时的变化。

### 20.2 本地目录

原始模板包保存在：

```text
.uidevtpl/<platform>/<framework>/<library>/<template>/
```

要求：

- 原始文件保持完整，便于后续 AI 继续参考。
- 项目运行时代码不能直接导入该目录。
- 同名目录已经存在时，先比对 manifest 和校验值。
- 版本不同或文件被修改时，先报告差异。
- 不能静默覆盖用户保留的旧模板参考。

### 20.3 `migration.json`

AI 迁移后至少记录：

```json
{
  "schemaVersion": 1,
  "template": {
    "id": "web/react/shadcn/quiet-grid",
    "version": "1.0.0",
    "family": "quiet-grid@1.0.0"
  },
```

### 20.4 迁移权限与停止条件

迁移任务允许 AI 新建文件、安装模板声明的兼容依赖、增量调整 Provider、全局样式、字体、路径别名和构建配置，并运行项目已有门禁。

出现以下情况时必须暂停并取得用户明确同意：

- 覆盖用户文件或未提交改动。
- 删除依赖、升级主要版本或替换组件库。
- 切换包管理器、构建工具、路由方案或样式系统。
- 删除项目文件、改变部署方式或执行不可恢复操作。
- 启动开发服务器或申请额外系统权限。

迁移结束后必须更新 `migration.json`，并报告依赖、配置、文件映射、验证结果和回退方式。

## 21. 代码质量要求

### 21.1 通用要求

- TypeScript 开启 `strict`。
- React 实现通过 `tsc`；Vue 实现通过 `vue-tsc` 或等价严格检查。
- 公开 API 具有明确类型。
- 禁止大面积 `any`、隐式全局状态和隐藏副作用。
- 文件按职责拆分，单文件不能堆积整套页面和全部组件逻辑。
- 导入方向符合分层规则。
- 不存在循环依赖和未声明依赖。
- 构建产物不依赖 Showcase 的演示数据。
- 核心运行路径没有控制台错误和未处理 Promise 错误。

### 21.2 测试边界

必须编写单元测试的内容：

- Schema 校验。
- token 转换和主题映射纯函数。
- 兼容性判断。
- 状态计算和重要纯函数。
- 迁移映射生成与校验。
- 检查规则和版本判断。

不编写外观单元测试的内容：

- 纯配色。
- 间距。
- 排版外观。
- 圆角与阴影。
- 静态布局细节。

这些视觉内容通过真实预览、固定视口截图和人工评审验证。键盘、弹窗、表单、焦点和状态切换使用浏览器交互测试。

## 22. 发布门禁

### 22.1 自动门禁

每个实现版本必须通过：

- `family.json` 和 `manifest.json` Schema 校验。
- 模板 ID、版本和源码目录一致性检查。
- 固定家族版本存在性检查。
- 必填 token 完整性检查。
- 组件能力与状态矩阵覆盖检查。
- 必须项和禁止项冲突检查。
- TypeScript strict 类型检查。
- 格式化、静态分析和生产构建。
- 导入方向、循环依赖和未声明依赖检查。
- shadcn `components.json`、底层组件依赖和 Registry Schema 一致性检查。
- 固定 ZIP 与 Registry Item 文件内容、依赖声明和校验值一致性检查。
- Vite React SPA 与 Next.js App Router 构建和迁移验证。
- Vite MPA 固定版本预览构建与深链验证。
- npm 与 pnpm 安装和锁文件一致性验证。
- 浏览器键盘交互和核心状态检查。
- 预览来源、iframe 权限和网络白名单检查。
- 360px、768px、1440px 溢出与遮挡检查。
- WCAG 2.2 AA 基础无障碍和颜色对比度检查。
- 模板包内容、路径和 SHA-256 检查。
- 固定包下载、解压和重复获取检查。
- `MIGRATION.md`、许可证和资产记录完整性检查。
- 网站预览源码与模板包版本一致性检查。
- MIT 模板代码许可证、品牌排除说明和 `ASSETS-LICENSE.md` 完整性检查。
- Codex 与 Claude Code 共 10 个受控任务至少成功 9 个，且没有静默覆盖、跳过校验、伪造结果或越权执行。

### 22.2 人工视觉门禁

人工评审至少检查：

- 模板具有明确且稳定的辨识度。
- 组件实验室和完整页面属于同一视觉语言。
- 两个不同题材的 Showcase 仍保持一致。
- 页面没有无意义卡片堆叠、装饰过量和文字层级失控。
- 真实业务主体清晰可见。
- 桌面、平板和手机都精致、可读、可操作。
- 长文案和极端数据不会破坏布局。
- Hover、Focus、Disabled、Loading、Error 和 Empty 状态完整。
- AI 使用模板完成未知题材后仍能延续风格。

### 22.3 发布证据

每个 `published` 版本保留：

- 自动门禁报告。
- 桌面、平板和手机参考截图。
- 人工视觉评审记录。
- 组件状态覆盖报告。
- 资产许可证清单。
- 模板包 URL、大小和 SHA-256。
- shadcn Registry Item URL、Schema、文件清单和校验记录。
- AI 迁移测试任务、目标项目和结果。
- 两名以上人工评审者的原始评分和复核记录。
- 版本变更说明。
- 跨框架实现存在时的 `PARITY.md`。

缺少任一强制证据时，状态只能保持 `draft` 或 `review`。

### 22.4 紧急下架

安全漏洞、许可证事故或错误模板包可以把发布记录的 `availability` 改为 `withdrawn`：

- 最新稳定入口、模板列表和 sitemap 排除该版本。
- 固定版本页保留最小身份、原因、时间和替代版本。
- 下载可以关闭，原 URL 不能换成其他文件。
- 模板包内 Manifest 和 SHA-256 保持不变。
- 修复后发布新版本，原版本的 `availability` 保持 `withdrawn`。
- 下架动作需要同时更新页面、缓存和下载入口，并保存操作记录。
